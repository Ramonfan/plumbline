# Development Workflow Specification

## Purpose

定义项目从需求受理、方案确认、开发执行、验证验收到交付归档的统一行为契约，确保需求、实现和证据可追溯，并使流程深度与实际风险匹配。

## Requirements

### Requirement: OpenSpec 是唯一事实源
项目 MUST 使用 OpenSpec 管理需求、行为规格、技术设计、任务进度、验收证据和归档结果，其他执行工具不得维护相互竞争的需求、设计或任务事实源。

#### Scenario: 创建行为变更需求
- **WHEN** 用户要求实现一个会改变可观察行为的需求
- **THEN** 执行者必须先创建或定位对应 OpenSpec change，并按任务等级维护所需工件

#### Scenario: 实施中发现方案变化
- **WHEN** 实现过程发现原设计、契约或范围需要调整
- **THEN** 执行者必须先更新 OpenSpec 工件并重新取得必要确认，再继续实施

### Requirement: 任务按风险分级
项目 MUST 将任务划分为 L0、L1、L2 或 L3，并采用匹配的工件、审查和验证深度。跨文件、跨仓或高连接度是评估信号，不得单独决定等级。

#### Scenario: 纯阅读任务
- **WHEN** 用户只要求查看、解释、梳理、审查或分析
- **THEN** 按 L0 处理，不创建 change、不修改实现，转实现时重新分级

#### Scenario: 小型低风险修复
- **WHEN** 范围明确、风险低且行为边界稳定
- **THEN** 按 L1 使用精简 proposal、行为 spec 和 tasks，design 按 CLI 条件与风险决定

#### Scenario: 常规行为需求
- **WHEN** 任务涉及常规功能、接口、UI、数据、缓存、权限或跨文件行为变化
- **THEN** 按 L2 使用完整 proposal、specs、design 和 tasks

#### Scenario: 核心改造
- **WHEN** 任务改变核心链路、架构、安全边界、显著公共契约或状态归属
- **THEN** 按 L3 补充影响分析、分阶段任务、回滚策略和匹配风险的验收矩阵

#### Scenario: 风险在实施中扩大
- **WHEN** 实施发现实际风险高于原等级
- **THEN** 必须提升等级并补齐工件，不得为减少流程继续沿用较低等级

### Requirement: 所有变更遵守三个门禁
进入实现的变更 MUST 通过需求门禁和方案门禁，准备归档的变更 MUST 通过交付门禁。

#### Scenario: 需求尚未确认
- **WHEN** 目标、非目标、范围或验收标准仍不明确
- **THEN** 不得完成方案或修改实现

#### Scenario: 用户允许落地
- **WHEN** 用户确认设计、任务、风险和验证方式，并明确允许执行
- **THEN** 可以按照 tasks 开始实施

#### Scenario: 自动验证完成
- **WHEN** 审查和自动验证已经通过，但人工业务、交互、视觉、设备或环境验收未完成
- **THEN** change 必须保持活跃并记录待验收项

#### Scenario: 用户完成验收
- **WHEN** 用户确认验收结果符合约定
- **THEN** 才能同步长期规格、补充交付记录并归档

### Requirement: Superpowers 仅服务开发执行
Superpowers MUST 按风险用于调试、测试、审查和完成前验证，不另行管理需求、设计、任务或归档。执行者 MUST 依据任务风险选择必要技能，不无差别增加流程。

#### Scenario: 缺陷根因未知
- **WHEN** 现象存在但根因没有证据支持
- **THEN** 使用系统化调试定位首次偏离预期的位置，不基于猜测修改

#### Scenario: 低风险局部改动
- **WHEN** 改动简单且没有复杂状态、安全、权限或公共契约风险
- **THEN** 使用本地审查和最窄有效验证，不自动增加独立审查或专项测试

#### Scenario: 高风险改动
- **WHEN** 改动涉及复杂异步、安全权限、公共接口、数据迁移或核心链路
- **THEN** 使用匹配风险的独立审查和完成前验证

### Requirement: 编码行为必须控制假设、复杂度和改动范围
执行者在修改实现前 MUST 明确影响方案的关键假设；多种解释会影响已确认契约或验收口径时必须先确认，不影响任何已确认契约或验收口径时 MUST 列出假设并继续，不得静默选择。实现 MUST 采用满足当前需求的最小方案，不引入未被要求的抽象、配置项、扩展点或未来能力；安全、权限、异步、迁移等风险明确要求的失败、取消、幂等和释放路径不属于过度设计。

执行者 MUST 只修改当前 change 授权范围内的代码和文档，不顺手重构、格式化、修改注释或整理无关内容。本次改动产生的未使用导入、变量、函数或文件 MUST 清理；既有死代码 MUST 只记录在当前 change 的残留风险或交付记录后续事项中，不得擅自删除。每个改动簇或逻辑单元 MUST 能追溯到当前 task 或已确认的 change 范围；生成产物、锁文件和工具强制的格式变更可以保留，但 MUST 说明来源、范围和验证方式，并仍须遵守工作区保护对生成产物和锁文件的授权要求。

任务 MUST 以可验证目标表达；完成声明 MUST 引用覆盖当前版本的实际检查、测试或其他证据，不得用主观判断代替。

#### Scenario: 需求存在多种解释
- **WHEN** 任务目标、输入范围、输出位置或成功标准存在多个合理解释
- **THEN** 影响已确认契约或验收口径时必须先请求用户确认；不影响任何已确认契约或验收口径时必须列出假设并继续，不得静默选择一种实现

#### Scenario: 发现更简单的实现路径
- **WHEN** 当前方案需要新增抽象、配置项或扩展点，而更小的方案已经满足当前需求
- **THEN** 执行者必须先说明更简方案，不引入未被要求的复杂度

#### Scenario: 目标附近存在无关代码
- **WHEN** 修改目标文件时发现相邻代码、注释、格式或无关文件有可改进空间
- **THEN** 本次改动不得顺手整理，只能记录或另行提出，除非用户明确授权扩大范围

#### Scenario: 本次改动产生孤儿代码
- **WHEN** 当前改动导致导入、变量、函数或文件不再被使用
- **THEN** 执行者必须清理本次改动产生的孤儿代码；现有死代码只能记录在当前 change 的残留风险或后续事项中，不得擅自删除

#### Scenario: 风险要求防御性处理
- **WHEN** 安全、权限、异步、数据迁移或核心链路要求失败、取消、重复进入、幂等或释放路径
- **THEN** 这些处理必须保留，不得以“最小实现”为由删除

#### Scenario: 任务完成声明
- **WHEN** 执行者准备声明任务完成、修复或通过
- **THEN** 必须给出可验证的成功标准，并引用覆盖当前版本的实际命令、测试或其他证据

#### Scenario: 生成产物或工具强制变更
- **WHEN** 当前任务需要更新生成产物、锁文件，或格式化工具会改动目标文件
- **THEN** 允许保留这些变更，但必须说明来源、范围和验证方式，不得用其掩盖无关改动

### Requirement: 保护工作区和仓库边界
执行者 MUST 在修改前确认实际仓库边界，并把现有未提交改动视为需要保留的外部状态。多仓工作区的状态、差异和验证 MUST 在实际受影响仓库分别执行。

#### Scenario: 目标文件已有无关改动
- **WHEN** 目标文件包含用户或其他任务的未提交内容
- **THEN** 本次修改必须保留这些内容，无法安全拆分时停止并请求处理方式

#### Scenario: 工作区包含多个仓库
- **WHEN** 一项任务影响两个或更多独立 Git 仓库
- **THEN** 分别记录每个仓库的状态、目标差异和验证结果，不使用工作区根目录代替

### Requirement: 验证证据绑定当前版本
每项完成声明 MUST 有覆盖当前实现、依赖和环境的验证证据。已有证据在相关内容未变化且没有新疑点时可以复用；变化、失败或新疑点出现后 MUST 重新验证。

#### Scenario: 修复构建错误
- **WHEN** 任务目标是修复编译、构建、迁移或部署失败
- **THEN** 修复后必须执行对应真实命令，不能用静态检查替代

#### Scenario: 自动化无法覆盖人工体验
- **WHEN** 行为依赖真实设备、浏览器、外部环境、交互或视觉结果
- **THEN** 保留人工验收任务，并明确自动验证没有覆盖该结果

### Requirement: 上下文与执行成本按风险控制
执行者 MUST 优先减少重复上下文、重复文档、重复验证和无意义轮询，不得以节省成本为由省略行为规格、用户门禁或必要验证，也不得把复杂任务默认降为低推理深度。

#### Scenario: L0 或 L1 启动
- **WHEN** 任务属于只读分析或低风险局部修复
- **THEN** 默认只读取目标 change、直接相关实现和必要主规格

#### Scenario: 长命令运行
- **WHEN** 构建、测试或部署命令需要较长时间
- **THEN** 完整日志写入文件并按合理间隔或完成事件等待，只报告新增进展和最终结果

### Requirement: 交付和周报可追溯
项目 MUST 在 change 中记录影响范围、实际改动、提交或补丁、验证命令、人工验收、残留风险和后续事项。周报 MUST 只统计当前周期发生状态变化的事项。

#### Scenario: 输出收益总结
- **WHEN** 用户要求说明改造收益
- **THEN** 输出改造前后链路、量化指标、变量定义、示例数据、适用前提和风险；无真实数据时明确标注估算口径

#### Scenario: 汇总周期周报
- **WHEN** 生成周报
- **THEN** 从活跃 change、archive 和必要历史记录提取本周期新增、完成、验收或状态变化，不重复统计无进展事项
