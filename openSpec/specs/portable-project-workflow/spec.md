# Portable Project Workflow Specification

## Purpose

定义一套可独立维护并安全安装到其他代码项目的研发工作流，使目标项目复用 OpenSpec 事实源、任务分级、用户门禁、按风险实施验证和交付归档，同时把技术栈与业务规则隔离到项目配置层。

## Requirements

### Requirement: 独立项目作为模板权威源
工作流 MUST 沉淀在独立目录中，并由根级协作规则、项目配置、使用说明、变更日志和 OpenSpec 自行管理。可安装模板 MUST 位于独立项目的模板目录中，后续修改应先在权威源完成并验证，不能依赖某个业务项目中的临时副本作为唯一来源。

#### Scenario: 维护工作流版本
- **WHEN** 使用者调整通用门禁、项目配置字段、安装方式或验证规则
- **THEN** 变更必须在独立工作流项目中通过 OpenSpec change 管理，并更新变更日志和模板版本说明

#### Scenario: 业务项目保留历史副本
- **WHEN** 原业务工作区仍保留工作流模板副本
- **THEN** 该副本可以作为历史依据保留，但后续复用和维护必须以独立项目中的模板为准

### Requirement: 模板采用通用核心与项目配置分层
模板包 MUST 将跨项目稳定的治理规则放入通用核心，将项目名称、仓库边界、技术栈、命令、运行环境、人工验收和禁止操作放入独立项目配置层。通用核心不得依赖任何业务项目的模块、类名或产品规则。

#### Scenario: 应用于非 iOS 项目
- **WHEN** 使用者把模板安装到 Web、后端或其他技术栈项目
- **THEN** 使用者只需填写项目配置和领域规格，不需要删除移动端依赖或业务专属规则

#### Scenario: 应用于 iOS 项目
- **WHEN** 使用者参考模板内的 iOS 示例填写项目配置
- **THEN** 多仓边界、依赖管理、真机 SDK 和人工真机验收等规则只进入该项目配置，不改变通用核心

### Requirement: 模板提供可识别的工作流基线
可安装模板 MUST 包含机器可读的工作流基线文件，并在新项目安装时将该文件复制到目标项目。基线 MUST 至少标识格式版本、工作流版本和权威项目名称，使消费项目能够记录当前接入版本并在人工升级时比较来源差异。

#### Scenario: 新项目完成安装
- **WHEN** 使用者向无冲突的空目标安装工作流
- **THEN** 目标项目必须包含可解析的基线文件，且其工作流版本与本次模板包一致

#### Scenario: 消费项目比较升级基线
- **WHEN** 使用者准备把消费项目升级到新的工作流模板
- **THEN** 使用者能够比较消费项目和权威模板中的基线文件，并按安装说明人工审查增量

#### Scenario: 已有项目缺少基线文件
- **WHEN** 历史消费项目没有基线文件
- **THEN** 升级说明必须要求使用者先确认实际来源和适用版本，再人工补充基线，不得自动推断或覆盖现有治理文件

### Requirement: 模板保留完整治理闭环
模板核心 MUST 定义 L0～L3 任务分级、需求门禁、方案门禁和交付门禁，并规定 OpenSpec 管理需求、行为规格、设计、任务、证据和归档，Superpowers 仅按风险参与调试、测试、审查和完成前验证。

#### Scenario: 只读分析任务
- **WHEN** 用户只要求查看、解释、梳理或分析
- **THEN** 项目按 L0 处理，不创建 change、不修改实现，后续转实现时重新分级

#### Scenario: 行为变更任务
- **WHEN** 用户要求修改可观察行为
- **THEN** 项目必须先定位或创建 OpenSpec change，通过需求与方案门禁后实施，并在用户完成交付验收后才能归档

#### Scenario: 自动验证完成但人工验收未完成
- **WHEN** 代码审查和自动验证已经通过，但业务、交互、视觉或部署环境验收尚未完成
- **THEN** change 必须保持活跃并记录待验收项，不得提前归档

### Requirement: 项目配置覆盖执行边界
项目配置模板 MUST 提供项目身份、代码与 Git 边界、技术栈、构建测试命令、验证矩阵、运行环境、领域规格索引、禁止操作和交付方式的明确填写位置。根级协作规则 MUST 指示执行者优先读取已填写的项目配置。

#### Scenario: 多仓工作区
- **WHEN** 一个工作区包含多个独立 Git 仓库
- **THEN** 项目配置能够列出各仓职责，验证和差异检查必须在实际受影响仓库分别执行

#### Scenario: 未填写必需变量
- **WHEN** 模板仍包含项目名称、仓库边界或验证命令等必需占位变量
- **THEN** 安装检查必须将其报告为未完成项，不能宣称工作流已经可用

### Requirement: 模板提供共享事实源的跨 agent 入口
可安装模板 MUST 同时提供面向 Codex/通用 agent 的 `AGENTS.md` 入口和面向 Claude Code 的 `CLAUDE.md` 入口。`CLAUDE.md` MUST 通过导入引用 `AGENTS.md` 和 `PROJECT_PROFILE.md`，不得复制或另行维护一套需求、门禁、任务或项目规则。两个入口 MUST 在安装、冲突检测和结构验证中被视为同一模板包的一部分；任一入口已存在时 MUST 零写入停止并要求人工合并。

#### Scenario: Codex 或通用 agent 使用项目
- **WHEN** 执行者读取根目录 `AGENTS.md`
- **THEN** 获得完整项目规则，不依赖 `CLAUDE.md` 是否存在

#### Scenario: Claude Code 使用项目
- **WHEN** Claude Code 读取根目录 `CLAUDE.md`
- **THEN** 通过 `@AGENTS.md` 和 `@PROJECT_PROFILE.md` 获得同一规则源，不出现第二套规则

#### Scenario: 安装到空项目
- **WHEN** 目标项目没有 `AGENTS.md` 和 `CLAUDE.md`
- **THEN** 安装同时生成两个入口文件，且 `CLAUDE.md` 只包含事实源说明、导入和必要的 Claude 专属补充位置

#### Scenario: 目标项目已有 CLAUDE.md
- **WHEN** 安装前检测到目标项目已有 `CLAUDE.md`
- **THEN** 安装列出冲突并以冲突状态零写入停止，要求人工比较合并

#### Scenario: 验证跨 agent 入口
- **WHEN** 运行模板验证
- **THEN** 检查两个入口存在、`CLAUDE.md` 的导入位于列 0 且每项恰好一次，根入口与模板入口一致，且模板 `CLAUDE.template.md` 未复制 `AGENTS.md` 的标题或正文规则

### Requirement: 安装过程保护现有项目文件
模板 MUST 提供人工安装和安全安装工具，默认不得覆盖目标项目已有的 `AGENTS.md`、`CLAUDE.md`、OpenSpec 配置、长期规格、CI 或构建脚本。安装工具 MUST 支持在不写入的情况下预览目标文件；存在同名文件时 MUST 报告全部冲突并停止。安装工具还 MUST 在写入前检查所有计划文件和目录输出，拒绝目标根目录内部的符号链接路径和非目录父路径。冲突或不安全路径失败时，目标目录及符号链接指向位置 MUST 零新增、零修改。

#### Scenario: 目标项目已有治理文件
- **WHEN** 目标项目已经存在 `AGENTS.md` 或 OpenSpec 目录
- **THEN** 安装说明要求先备份和差异合并，不得把模板文件直接覆盖为唯一版本

#### Scenario: 新项目首次安装
- **WHEN** 目标项目没有现有治理文件且目标文件父路径均为普通目录或尚不存在
- **THEN** 使用者可以先预览安装，再复制缺失文件和工作流基线、替换变量、初始化 OpenSpec 并运行结构校验

#### Scenario: 安装目标存在同名文件
- **WHEN** 安装工具发现一个或多个目标文件已经存在
- **THEN** 安装必须列出全部冲突，以约定的冲突状态结束，并且不得创建或修改任何目标文件或目录

#### Scenario: 目标父路径包含符号链接
- **WHEN** 任一计划文件或目录输出自身或其既有父路径是符号链接
- **THEN** 安装必须报告不安全路径并在写入前以非成功状态结束，目标根目录和链接指向位置均不得新增或修改内容

#### Scenario: 目标父路径不是目录
- **WHEN** 任一计划文件或目录输出的既有父路径是普通文件或其他非目录对象
- **THEN** 安装必须报告不安全路径并在写入前以非成功状态结束，目标目录不得新增或修改内容

#### Scenario: 重复安装
- **WHEN** 使用者对已经完成安装的目标再次运行安装工具
- **THEN** 安装必须把全部已安装目标报告为冲突并零写入退出，不得把重复运行视为升级

### Requirement: 模板提供可复核的验收方式
独立项目 MUST 提供可重复执行且不依赖本机专属绝对路径的校验入口，覆盖目录清单、基线文件解析、占位变量范围、业务专名隔离、配置解析、安全安装行为和 OpenSpec strict validation。安全安装验证 MUST 覆盖预览、空目标安装、部分冲突零写入、重复安装和符号链接父路径拒绝。验证结果 MUST 区分模板结构验证与目标项目自身的构建、测试或人工验收。

#### Scenario: 使用默认临时目录验证模板
- **WHEN** 使用者在项目根目录运行统一校验且未指定临时目录
- **THEN** 校验必须使用通用系统临时目录完成全部检查并清理自身临时产物

#### Scenario: 使用自定义临时目录验证模板
- **WHEN** 使用者通过环境指定一个可写临时目录
- **THEN** 校验必须只在该临时目录下创建测试产物，完成后清理，并输出统一成功标志或明确失败原因

#### Scenario: 验证模板自身
- **WHEN** 模板包生成完成
- **THEN** 校验入口必须检查必需文件完整、基线字段有效、占位变量集中、通用文件不含业务专名，并验证配置格式、安装预览、正常安装、冲突零写入、符号链接路径拒绝和 OpenSpec 结构

#### Scenario: 验证目标项目接入
- **WHEN** 使用者在另一个项目完成模板适配
- **THEN** 必须运行该项目配置中定义的实际构建、测试、静态检查和人工验收，不能用模板结构校验代替项目验证

### Requirement: 消费项目的通用流程改进回流权威项目
安装或引用本工作流的项目 MUST 在项目配置中记录权威工作流来源。消费项目发现流程改进时 MUST 判断其通用性：具备跨项目价值的改进必须通过权威工作流项目的 OpenSpec change 同步到模板、规格、验证和变更日志；技术栈、业务模块或单项目专属规则必须留在消费项目的项目配置或领域规格中。

#### Scenario: 发现通用流程缺口
- **WHEN** 消费项目改进任务分级、门禁、工件职责、安装行为、验证方法或交付规则，且该改进不依赖项目专属业务
- **THEN** 消费项目的流程 change 必须记录关联的权威项目 change，并在交付前完成同步或明确记录经用户确认的延期安排

#### Scenario: 发现项目专属规则
- **WHEN** 改进仅适用于某个技术栈、仓库结构、业务模块或运行环境
- **THEN** 规则只能进入该项目的 `PROJECT_PROFILE.md`、领域主规格或权威项目中明确标记的示例，不得改变通用核心默认行为

#### Scenario: 流程 change 准备交付
- **WHEN** 消费项目的流程或项目治理 change 已完成实施与自动验证
- **THEN** 交付记录必须包含“已同步到权威项目”或“无需同步及原因”，缺少同步结论时不得通过交付门禁

#### Scenario: 两端安全同步
- **WHEN** 权威项目和消费项目需要交换流程改进
- **THEN** 必须通过关联 change 人工审查差异并在两端分别验证，不得自动跨项目覆盖文件

### Requirement: 已接入项目可安全升级工作流
权威工作流项目 MUST 提供只读的升级差异比较能力，帮助已接入项目比较当前文件、权威模板和可选的旧基线模板快照。比较结果 MUST 至少区分文件一致、仅消费项目修改、仅模板修改、双方修改、已收敛和缺失文件；项目配置和 agent 入口等专属文件 MUST 标记为人工处理。比较过程 MUST NOT 写入目标项目、旧模板快照或权威模板。权威项目 MUST 为每个可接入版本提供可追溯的模板快照，并在比较前确认模板工作区对应目标版本且无未提交改动。消费项目升级 MUST 通过自身 OpenSpec change 管理，并在人工合并、真实项目验证和用户验收完成后才更新记录的接入基线。

#### Scenario: 消费项目与当前模板一致
- **WHEN** 已接入项目运行只读比较且所有目标文件与当前模板一致
- **THEN** 报告所有文件为一致状态，不要求合并

#### Scenario: 只有消费项目修改
- **WHEN** 提供正确的旧基线模板快照，目标文件相对旧快照有本地修改，而当前模板未修改该文件
- **THEN** 报告为仅消费项目修改，建议保留本地内容

#### Scenario: 只有模板修改
- **WHEN** 提供正确的旧基线模板快照，当前模板修改了文件，而目标文件与旧快照一致
- **THEN** 报告为仅模板修改，提示人工合并模板增量

#### Scenario: 双方都修改
- **WHEN** 目标文件和当前模板都相对旧快照发生变化且内容不同
- **THEN** 报告为双方修改，要求人工三方合并并记录决策

#### Scenario: 目标文件缺失
- **WHEN** 目标项目缺少映射中的文件
- **THEN** 报告为缺失，不以成功状态宣称已安装完整

#### Scenario: 没有旧基线快照
- **WHEN** 消费项目无法提供旧基线模板快照
- **THEN** 比较 MUST 降级为两方比较，并明确提示无法区分本地修改和模板修改，要求人工审查

#### Scenario: 比较过程只读
- **WHEN** 比较脚本运行成功或失败
- **THEN** 目标项目、旧模板快照和权威模板目录 MUST 零新增、零修改、零删除

#### Scenario: 升级完成后更新基线
- **WHEN** 消费项目完成模板增量合并、真实项目验证和用户验收
- **THEN** 才允许更新消费项目 `PROJECT_PROFILE.md` 记录的接入基线和 `WORKFLOW_BASELINE.yaml`，并归档对应 OpenSpec change

### Requirement: 权威项目名称在事实源中保持一致
权威工作流项目 MUST 在项目配置、模板基线、公开文档和 OpenSpec context 中使用同一个正式名称。模板 `WORKFLOW_BASELINE.yaml` 的 `authority_name` MUST 为机器可读英文名称 `Plumbline`，并与 `PROJECT_PROFILE.md` 记录的项目名称指向同一项目。此处 OpenSpec context 指 `openSpec/config.yaml` 的 `context` 字段；CLI 显示的目录名不因改名自动变化。改名 MUST NOT 改变安装映射、占位符范围、安装或比较退出码，也 MUST NOT 改写历史归档记录。消费项目记录的权威来源可以在人工确认后更新，不得由本项目的升级流程自动覆盖。

#### Scenario: 基线名称与项目配置一致
- **WHEN** 校验模板基线和项目配置
- **THEN** `authority_name` 为 `Plumbline`，并与项目配置记录的项目名称指向同一项目，验证通过

#### Scenario: 公开文档使用正式名称
- **WHEN** 阅读根目录文档、`openSpec/config.yaml` 的 context 字段和模板安装说明
- **THEN** 使用同一个正式名称，不出现互相冲突的项目身份

#### Scenario: 改名不改变安装契约
- **WHEN** 项目完成改名
- **THEN** 安装文件映射、占位符范围、安装退出码、比较分类语义和升级流程保持不变

#### Scenario: 历史记录不改写
- **WHEN** 项目改名后查看归档 change
- **THEN** 历史 change 保留原名和原有内容，新名称从改名 change 起生效

#### Scenario: 消费项目来源人工更新
- **WHEN** 消费项目需要跟随权威项目改名
- **THEN** 由消费项目人工更新记录的权威来源，不由权威项目自动写入
