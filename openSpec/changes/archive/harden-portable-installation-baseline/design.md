## Context

现有安装器先检查七个目标文件冲突，再逐个创建父目录并复制；现有验证器在 `/private/tmp` 建立测试目录，并用完整安装后的文件哈希比较证明重复安装没有修改文件。该实现能够覆盖当前 macOS 环境的基本行为，但没有模板版本标识，也没有验证部分冲突空目标、目录新增或父路径符号链接。动机和需求边界见 `proposal.md` 与 delta spec。

## Goals / Non-Goals

**Goals:**

- 不改变 `install.sh --target <dir> [--dry-run]` 接口，收紧写入前安全检查。
- 使用单一、机器可读、随模板安装的版本基线支持人工升级比较。
- 使验证临时目录适配 macOS 和常见 Linux 环境，并允许调用方指定临时目录。
- 用可复核的测试证明预览、正常安装、部分冲突、重复安装和符号链接路径的行为。

**Non-Goals:**

- 不实现覆盖、合并、自动升级或自动回滚。
- 不保证复制阶段发生磁盘故障时的事务原子性；本 change 保证的是预检可发现条件下的零写入。
- 不自动修改已有消费项目，也不根据已有文件推断其历史版本。
- 不引入新的运行时、包管理器或第三方依赖。

## Decisions

### 1. 使用 `WORKFLOW_BASELINE.yaml` 作为公开基线文件

在 `templates/project-workflow/WORKFLOW_BASELINE.yaml` 保存：

```yaml
schema_version: 1
workflow_version: 0.1.0-dev.1
authority_name: AI 工作流
```

安装时原名复制到目标项目根目录。`schema_version` 负责文件格式演进，`workflow_version` 使用 SemVer 兼容格式，未正式发布阶段使用预发布标识，`authority_name` 便于人工确认来源。验证器解析 YAML、校验字段类型和值，并确认安装结果与模板源一致。

选择 YAML 是因为项目已经使用 Ruby 解析 YAML，无需增加依赖；相比把版本仅写在 README 或 `CHANGELOG.md` 中，它更适合机器校验；相比安装时生成带日期的清单，静态文件能够稳定比较且不会引入不可重复输出。

### 2. 安装预检按“模板完整性 → 路径安全 → 目标冲突 → 计划输出 → 写入”执行

目标根目录继续通过物理路径规范化。安装计划显式包含八个文件目标和 `openSpec/changes/archive` 目录目标。对文件目标检查全部父路径，对目录目标检查包括目录自身在内的每一级既有组件；任一组件为符号链接或非目录对象时，收集并报告相对路径，以状态 `73` 退出。目标文件自身为符号链接仍按现有冲突处理，以状态 `2` 退出。所有检查必须在 `mkdir` 或 `cp` 前完成。

普通既有目录允许复用，不存在的父目录留到写入阶段创建。这样既阻止通过 `openSpec -> /other/path` 把文件写出目标根目录，也不影响常规项目提前创建 `openSpec/` 的使用方式。

备选方案是对每个最终目标使用 `realpath` 比较前缀，但不同平台的 `realpath` 选项不一致，且不存在的目标无法统一解析；逐级检查现有父路径只依赖 Bash 文件测试，兼容性更好。另一个备选方案是完全拒绝目标内任何符号链接，但范围过宽，本 change 只拒绝会承载计划写入的父路径。

### 3. 临时目录以环境为入口并在使用前规范化

验证器读取 `${TMPDIR:-/tmp}`，确认它是可写目录，转换为物理路径后调用 `mktemp -d "$tmp_base/ai-workflow-verify.XXXXXX"`。清理函数只删除规范化临时基目录下、且名称匹配固定前缀的目录。

相比固定 `/private/tmp`，该方案能适配 macOS、Linux 和受控 CI；相比直接信任未规范化的 `TMPDIR`，先解析物理路径可以让清理边界可判断。若临时目录无效，验证必须在创建测试产物前明确失败。

### 4. 用完整树快照验证零写入

验证器建立三个相互隔离的目标：

- 空目标：验证 dry-run 后树为空，并验证正式安装后的全部文件映射和基线内容。
- 部分冲突目标：只预置两个目标文件，记录包含文件类型、相对路径和文件校验值的树快照；执行安装后断言状态为 `2`、错误输出包含两个冲突、前后快照完全一致。
- 符号链接目标：在目标中创建 `openSpec` 父路径符号链接到同一临时根下的外部目录，分别记录目标和外部目录快照；执行安装后断言状态为 `73`、错误包含不安全路径、两棵树均未变化。

重复安装继续使用完整安装目标，但同样改用完整树快照，并断言所有目标文件均出现在冲突输出中。快照使用项目已有 shell 工具生成，不跟踪所有权、时间戳等与内容安全无关的元数据。

### 5. 文档和升级流程保持人工合并

安装说明新增基线文件映射，并要求消费项目把 `workflow_version` 记录到 `PROJECT_PROFILE.md` 的“当前接入版本、标签或基线”。历史项目升级时先确定其真实来源；无法确认时标记为“历史基线未知”，比较当前文件后再补入基线，不能把最新版本直接冒充历史版本。

模板公开参数和既有目标文件不删除、不重命名。新增基线文件会使已经存在同名文件的目标进入正常冲突流程，这是预期的保护行为。

### 6. Archify 图采用双泳道单向主流程

工作流图使用 `workflow` schema v2 和 `showcase` 质量配置，压缩为“OpenSpec 治理与用户门禁”“实施与验证”两条泳道。需求工件与需求门禁、方案工件与方案门禁分别合并为同一节点，既保留三个门禁和 OpenSpec 权威关系，又满足 1440×900 到 2048×1320 的桌面首屏可读性。主流程保持单向，只保留“验证或审查失败返回实施”的一条修正回路；L0 只读、L1–L3 变更和消费项目回流在对应节点中显式标注。

图的 JSON 规格和 HTML 放在独立可视化工作区，不加入可安装模板，也不成为第二套需求事实源。OpenSpec change 只记录图的路径、校验收据和浏览器证据。若 Archify showcase 校验不通过，不得把草图描述为正式交付图。

## Risks / Trade-offs

- [部分合法项目使用符号链接承载 `openSpec/`] → 安全安装器明确拒绝，安装说明提供人工审查和逐文件合并路径，不静默跟随链接。
- [静态版本文件可能忘记随行为变化更新] → `verify.sh` 校验文件存在、格式和值，并在变更清单中把基线与 `CHANGELOG.md` 更新放在同一任务；后续发布流程仍需人工决定版本增量。
- [不同平台 `mktemp` 行为存在差异] → 只使用 BSD/GNU 都支持的“目录模板包含六个 X”形式，并通过自定义 `TMPDIR` 的交付验证补充证据。
- [复制阶段意外失败仍可能留下部分新文件] → 本 change 不承诺事务式安装；安装器保持逐文件复制，失败时报告实际状态，未来如需原子安装应作为独立 L3 change 设计回滚协议。
- [版本 `0.1.0-dev.1` 尚非正式发布] → 基线明确使用预发布标识；正式发布另行通过版本 change 更新，不在本 change 中创建标签或发布。
- [可视化布局可能与流程语义竞争] → 保留单向主链和最多十二个节点；语义以 OpenSpec 规格为准，图只做可验证的阅读辅助。

## Migration Plan

1. 在模板中加入 `WORKFLOW_BASELINE.yaml`，同步安装映射、文档和验证规则。
2. 先扩展验证场景并确认它们能暴露当前实现缺口，再修改安装和临时目录实现。
3. 运行默认临时目录与自定义临时目录两轮完整校验，并执行 OpenSpec strict validation。
4. 已有消费项目不自动升级；维护者按 `INSTALL.md` 比较增量，确认真实历史来源后复制基线文件并更新本地 `PROJECT_PROFILE.md`。
5. 若实施结果不满足验收，在未归档状态回退本 change 涉及的新增映射和脚本改动；已有消费项目不受影响，因为本项目不会自动写入它们。

## 兼容矩阵

| 场景 | 预期结果 |
|---|---|
| 普通空目录 | 预览零写入，正式安装成功并包含基线文件 |
| 已有一个或多个目标文件 | 列出全部冲突，状态 `2`，完整树不变 |
| 已完成安装后重复运行 | 所有目标均冲突，状态 `2`，完整树不变 |
| 目标父路径是符号链接 | 报告不安全路径，状态 `73`，目标与链接指向位置均不变 |
| 目标父路径是普通文件 | 报告不安全路径，状态 `73`，目标目录树不变 |
| 未设置 `TMPDIR` | 在 `/tmp` 下建立并清理验证目录 |
| 设置有效 `TMPDIR` | 只在指定目录下建立并清理验证目录 |
| 历史消费项目无基线 | 人工确认来源并合并，不自动推断或覆盖 |
