# 审查契约

汇总 findings 和给出 verdict 前读取本文件。

## 严重级别

- **Critical**：稳定崩溃、核心链路不可用、数据丢失或串用、严重安全隐私问题、不可逆状态破坏，或明确违反已确认的 MUST 规格。
- **Important**：需求偏离、明显回归、兼容破坏、竞态、生命周期错误、资源泄漏、重要边界失败，或必需验证缺失。
- **Minor**：可读性、局部维护成本、低概率低影响边界或非阻断性能细节。

严重级别按影响和触发条件判定，不按改动行数或修复成本判定。

## Finding 字段

每项 finding 包含：

- 编号：`CR-<Critical|Important|Minor>-NNN`
- 位置：相对路径与行号，或精确命令与文件字段
- 影响：用户或系统可观察的后果
- 触发条件：什么输入、时序、权限或环境会触发
- 依据：对应规格条款、任务、项目规则或实际命令输出
- 处理方向：修复、补证据、补验收或明确接受

无法给出可定位证据的担忧放入「未覆盖项」，不得制造 finding。

## Verdict 条件

`Ready: Yes` 必须同时满足：

1. 范围明确，且只包含当前 change 的改动；
2. 没有未解决的 Critical/Important；
3. 方案门禁已通过；
4. 必需验证覆盖当前源码、依赖和环境版本；
5. 项目要求的独立审查由一个未参与实现、且不持有实现者结论的 reviewer 完成。

同一执行者清空上下文、换角色复述或自称「独立视角」不算独立审查。无法证明 reviewer 独立时，按未完成处理。

任一条件不满足即为 `Ready: No`。`Yes` 不表示已获提交、推送、合并或发布授权，也不表示用户验收完成。

## 输出模板

```markdown
## 代码审查结论

- Change：<名称或“无 change”>
- 任务等级 / 方案门禁：<L1|L2|L3> / <已通过|未通过|无法确认>
- 审查方式：<本地审查|独立审查>
- 范围：<仓库与 diff/base-head>

### 需求映射

| 规格或任务 | 结论 |
|---|---|
| <条款> | <满足|偏离|未实现> |

### Findings

| 编号 | 级别 | 位置 | 影响 | 触发条件 | 依据 | 处理方向 |
|---|---|---|---|---|---|---|

无 finding 时写「无」。

### 验证证据

- <命令 + 退出码 + 覆盖范围，或「复用既有证据：...」，或「缺失：...」>

### 残留风险、未覆盖项与人工验收

- <逐项列出；没有时写「无」>

**Ready: No**
```

固定使用 `Ready: Yes` 或 `Ready: No`，不输出第三个状态。

## 回写格式

技术审查保持只读。审查结束后，若用户授权记录，执行者把以下块写入当前 change 的 `tasks.md`，作为独立交接步骤；不要写入其他文件，也不要另建结论文件。

```markdown
### 代码审查记录

- 范围：
- 审查方式：
- 验证引用：
- Critical：0
- Important：0
- Minor：
- 残留风险与未覆盖项：
- 人工验收：
- Ready: No
```
