# {{PROJECT_NAME}} 项目协作与交付约束

本文件是项目根级执行约束。开始任何任务前，先读取本文件和根目录 `PROJECT_PROFILE.md`；进入子目录时，再叠加该目录更细的 `AGENTS.md`。Codex 会沿目录向上扫描 `AGENTS.md`；Claude Code 通过根 `CLAUDE.md` 导入根 `AGENTS.md`，默认只读 `CLAUDE.md` 链路，子目录 `AGENTS.md` 需在该子目录提供薄 `CLAUDE.md` 或启用 `claude-md-and-agents-md` 才会一并加载。规则冲突时，用户当前明确指令优先，其次是更具体目录规则，再其次是根级规则。

## OpenSpec、Superpowers 与执行者职责

- **OpenSpec**：管理需求、可观察行为规格、技术设计、任务进度、验收证据、长期主规格同步和归档，是项目唯一事实源。
- **Superpowers**：只提供测试驱动开发、系统化调试、代码审查和完成前验证，不另行管理需求、设计、任务状态或归档。
- **执行者**：负责判断任务等级、创建或定位 OpenSpec change、执行已确认方案、按风险使用 Superpowers，并把实现与验证结果回写 OpenSpec。
- **PROJECT_PROFILE.md**：记录项目名称、仓库边界、技术栈、命令、运行环境、领域规格和禁止操作。不得把项目专属规则反向散落到通用流程文件。

新流程统一使用 OpenSpec 的 `spec-driven` schema。官方目录为 `openSpec/config.yaml`、`openSpec/specs/`、`openSpec/changes/` 和 `openSpec/changes/archive/`。

## 任务分级

- **L0 阅读分析**：用户只要求查看、解释、梳理、审查或确认逻辑。只读必要上下文并输出结论，不创建 change、不修改实现；后续进入实现时重新分级。
- **L1 小型修复**：范围明确、低风险的局部修复。使用精简 proposal、行为 spec 和 tasks；design 仅在 CLI 条件或风险需要时生成最小有效版本，验证证据集中记录在 tasks。
- **L2 常规需求**：功能、UI、接口、数据结构、缓存、路由、权限、部署行为或跨文件行为变化。使用完整 proposal、specs、design 和 tasks。
- **L3 核心改造**：涉及核心链路、架构、显著公共契约、安全边界或状态归属变化。除完整工件外，还必须补充影响分析、分阶段任务、回滚策略和匹配风险的验收矩阵。

跨仓、跨文件和高连接度是风险信号，不单独决定等级。实施中发现范围或风险扩大时只能提升等级，不得为减少流程而降级。

## 三个门禁

1. **需求门禁**：目标、非目标、影响范围和验收标准确认后，才能完成 proposal 和行为规格。
2. **方案门禁**：设计、任务、兼容策略、风险和验证方式确认后，用户明确表达“可以、落地、执行”或同等意图，才能修改实现。
3. **交付门禁**：代码审查门禁给出 `Ready: Yes` 且自动验证通过后，由用户完成项目要求的业务、交互、视觉、部署或运行环境验收；用户确认前不得归档。

纯文档或项目治理 change 可在审查和 strict validation 后预同步主规格供用户结构验收，但用户确认前仍不得归档。

## 标准执行顺序

1. 读取 `PROJECT_PROFILE.md`，确认技术栈、实际仓库边界、命令和禁止操作。
2. 结合对话及必要的 `openspec list`、`openspec status` 定位 change；同目标同范围优先复用活跃 change。
3. 按任务等级和 CLI 当前指令生成 proposal、specs、design、tasks，不绕过 blocked 或必需依赖。
4. 用户通过方案门禁后按 tasks 实施；每完成一项立即更新 checkbox 和验证证据。
5. 原因未知的缺陷先系统化调试；已确认的验证选择和同范围授权不重复询问。
6. 按风险运行 `running-code-review-gate` 并执行最窄有效验证；相关实现变化、失败或新疑点出现后重新验证。
7. 流程或项目治理 change 在交付前完成通用性判断，记录权威项目同步结论及关联 change。
8. 用户通过交付门禁后同步 delta specs、补充交付记录并归档。

## 工作流改进回流

- `PROJECT_PROFILE.md` 必须记录当前项目使用的权威工作流来源和回流方式。
- 任务分级、门禁、OpenSpec 工件职责、安装、验证和交付等具备跨项目价值的改进，必须通过权威项目的 OpenSpec change 同步到模板、规格、验证和变更日志。
- 技术栈、仓库结构或运行环境专属规则只进入消费项目的 `PROJECT_PROFILE.md`、对应主规格或权威项目中明确标记的示例；业务模块和产品规则只留在消费项目。
- 流程或项目治理 change 的交付记录必须填写“已同步到权威项目”或“无需同步及原因”；需要同步时同时记录关联 change，缺少结论时不得通过交付门禁。
- 不自动跨项目覆盖文件；两端分别审查、实施和验证，避免破坏本地适配与未提交改动。

## OpenSpec 工件职责

- **proposal**：为什么做、目标、非目标、影响范围、验收口径和需求门禁结论。
- **specs**：用户或下游可以观察和验证的行为契约，不写逐步实现。
- **design**：职责、数据流、时序、关键决策、关键假设、更简替代方案、兼容、迁移、风险和验证方案。
- **tasks**：可独立完成并验证的实施任务、执行进度和证据；必须把任务写成可验证目标。

同一信息只保留在最合适的工件中，通过引用避免重复。行为变化必须有 spec；只有纯重构、工具或文档变化且确实没有规格行为变化时，才允许按 CLI 规则使用 `skip_specs`。

## 上下文与执行成本

- L0 默认只读直接相关文件、必要历史结论和 change 状态。
- L1 默认只读目标 change 工件和直接相关实现；仅在实际触及某领域时加载对应长期主规格。
- L2/L3、疑难缺陷、复杂异步、安全权限、公共契约和构建错误修复使用匹配的高推理深度；优先减少重复上下文、重复文档和重复验证。
- 已读取且版本、schema 和内容未变化的静态指令可复用；当前状态、依赖、路径、blocked、警告和变化内容必须重新读取。
- 长命令完整日志写入临时文件，按 30～60 秒或完成事件等待；只报告新进展、关键错误和最终结果。
- 已有证据覆盖当前源码与依赖版本且无相关变化时可直接引用；不能为了汇报重复执行高成本验证。

## 工作区与文件保护

- 开始修改前确认实际 Git 仓库边界；多仓工作区必须分别检查受影响仓库。
- 未提交改动默认属于用户或其他任务，不得回退、覆盖、暂存、格式化或顺手整理无关文件。
- 不直接修改生成产物、依赖缓存、锁定目录或外部同步文件，除非 `PROJECT_PROFILE.md` 或用户明确授权。
- 修改前检查目标文件已有差异；存在重叠时保留无关内容，无法安全拆分则停止并说明。
- 删除、覆盖、回滚、迁移数据或修改外部系统前，先解析精确目标并确认已获得相应授权。
- 新增文件、命名、注释语言和目录位置遵守 `PROJECT_PROFILE.md` 及邻近代码既有模式。

## 编码行为准则

- 开始实现前明确写出影响方案的关键假设；多种解释会影响已确认契约或验收口径时必须先确认，不影响任何已确认契约或验收口径时列出假设并继续，不得静默选择。
- 采用满足当前需求的最小方案，不引入未被要求的抽象、配置项、扩展点或“以后可能用到”的能力。
- 只修改当前 change 授权范围内的代码和文档；不顺手重构、格式化、修改注释或整理无关内容，风格与邻近代码保持一致。
- 本次改动产生的未使用导入、变量、函数或文件必须清理；既有死代码只记录在当前 change 的残留风险或交付记录后续事项中，不擅自删除。
- 每个改动簇或逻辑单元都应能追溯到当前 task 或已确认的 change 范围；生成产物、锁文件和工具强制的格式变更可以保留，但必须在 tasks 或交付记录中说明来源、范围和验证方式，并仍须遵守工作区保护对生成产物和锁文件的授权要求。
- 把任务写成可验证目标：先定义成功标准，再实现并循环验证；不以“看起来可用”作为完成依据。
- 安全、权限、异步、数据迁移和核心链路要求的失败、取消、幂等、重试和释放路径不属于过度设计，仍须按项目风险保留。

## 实施原则

- 优先复用现有架构、组件、服务、工具类、错误处理和命名，不为局部问题引入新体系。
- 修改公共接口、数据契约、权限、安全、缓存、路由或持久化时，必须说明兼容、迁移、失败和回滚策略。
- 异步、订阅、定时器、监听器、资源句柄和后台任务必须有取消、释放、重复进入及过期结果处理路径。
- 关键注释解释业务意图、时序边界、兼容原因、状态归属或不可随意调整的约束，不复述代码。
- 涉及第三方库、框架、SDK 或不确定 API 时，先查阅当前官方文档；项目内部 API 以本地实现和既有调用为准。
- 发现设计缺口、额外需求或与已确认方案不一致时，先更新 OpenSpec 并重新通过必要门禁，不得在实现中静默扩大范围。

## 调试、测试、审查与验证

- 根因未知的缺陷使用系统化调试：记录现象与复现条件，比较正常和异常路径，定位首次偏离预期的位置，再确定最小修复。
- 默认采用项目现有的最窄有效验证。是否新增专项单测或采用完整 TDD，由方案阶段按风险决定并取得用户确认。
- 提交、合并或声明实现完成前，运行 `running-code-review-gate`；L1 默认本地审查，L2 按风险决定，复杂异步、权限、安全、公共接口及 L3 使用未参与实现的独立 reviewer。
- 审查结论固定给出 `Ready: Yes/No`；存在未解决的 Critical/Important、范围未知、方案门禁未过或必需证据缺失时必须为 `No`。审查通过不替代用户验收，也不授予提交或发布权限。
- 审查 skill 的技术审查默认只读；不自动修改实现、不执行 Git 写操作。用户授权记录时，结论和验证引用作为独立记录步骤写入当前 change，不建立第二事实源。
- 每个受影响仓库至少执行 `PROJECT_PROFILE.md` 定义的状态、差异和格式检查。
- 修复编译、构建、迁移或部署错误后，必须执行对应真实验证，不能用语法检查或静态检查替代。
- UI、交互、设备、浏览器、部署或生产等自动化无法覆盖的内容，保留人工验收任务；自动验证通过不等于交付完成。
- 完成前记录实际命令、结果、未执行原因、环境版本、无关脏改和残留风险。

## 交付记录

每个 change 在自动验证后至少记录：

```markdown
## 交付记录

- 影响仓库：
- 实际改动：
- 提交 / Patch：
- 自动验证命令与结果：
- 人工业务 / 交互 / 视觉 / 环境验收：
- 工作流同步结论：已同步到权威项目 / 无需同步及原因 / 不适用
- 关联权威项目 change：
- 未覆盖项与残留风险：
- 后续事项：
```

用户要求收益总结时，按“改造项、改造前后链路、量化指标、公式变量、示例数据、前提和风险”输出。没有真实线上数据时，明确标注为代码路径测算或估算。

## 周报与历史记录

- 周报使用 `openSpec/weekly_report_template.md`，只统计当前周期有新增、完成、验收或状态变化的事项。
- 活跃事项读取 `openSpec/changes/`，已完成事项读取 archive；历史格式文件仅作为追溯依据，不用于创建新任务。
- 新任务只在官方 change 目录中创建，不继续扩散旧模板或日期单文件。

## 项目专属规则入口

以下内容必须在 `PROJECT_PROFILE.md` 中定义并保持最新：

- 工作区和 Git 仓库边界；
- 主要源码、测试、配置、文档和生成产物目录；
- 技术栈、依赖管理和外部服务；
- 构建、测试、静态检查、格式检查和运行命令；
- 支持的本地、设备、测试、预发布和生产环境；
- 人工验收矩阵；
- 长期领域规格索引；
- 代码审查门禁的强制独立审查条件和项目专属检查点；
- 禁止修改和高风险操作；
- 发布、回滚和交付约束。

若 `PROJECT_PROFILE.md` 尚未完成或仍有必填占位符，不得宣称工作流安装完成。
