# 编码行为反例参考

> 参考 `multica-ai/andrej-karpathy-skills` README 中标注为 MIT 许可的四项原则，按本项目通用治理语境重新表述。本文件未复制该仓库原文；示例使用通用伪代码，不代表任何项目技术栈或业务规则。
>
> 本文件仅供合并 `AGENTS.md`、培训和审查时参考，不进入安装映射。

## 1. 隐藏假设

**用户请求：** “加一个导出用户数据的功能。”

**常见错误：** 直接假定导出全部用户、写入本地文件、只包含固定字段，并立即实现。

**应先确认：**

- 导出全部用户还是筛选后的子集？是否涉及隐私或权限？
- 需要浏览器下载、后台任务、邮件通知还是 API 返回？
- 包含哪些字段？哪些字段必须脱敏？
- 数据量级是多少？是否需要分页或异步处理？

如果没有额外信息，应先给出最小合理解释和需要确认的点，而不是静默选择。

## 2. 过度抽象

**用户请求：** “加一个折扣计算。”

**常见错误：**

```text
为单次折扣计算引入策略接口、百分比策略、固定金额策略、
配置对象、最小值、最大值和通知回调，最终需要几十行初始化代码。
```

**更小的方案：**

```text
function calculate_discount(amount, percent):
    return amount * percent / 100
```

只有当确实出现多种折扣类型时，再按实际需求重构。不要为“以后可能需要”提前建立抽象层。

## 3. 顺手重构

**用户请求：** “修复空邮箱导致校验崩溃的问题。”

**常见错误：** 顺便修改相邻注释、调整引号风格、增加类型标注、补充用户名长度校验，并重排整个函数。

**应只做：**

```text
读取邮箱字段
如果邮箱为空或只包含空白字符，抛出“邮箱必填”
保持其他校验、注释、格式和返回行为不变
```

如果发现相邻死代码或可改进点，在交付记录中说明，不擅自删除或重构。

## 4. 模糊目标

**用户请求：** “修复登录问题。”

**常见错误：**

```text
计划：
1. 查看代码
2. 找到问题
3. 修改实现
4. 测试一下
```

**应改成可验证目标：**

```text
现象：修改密码后旧会话仍然有效。
成功标准：修改密码后旧会话立即失效，新会话可正常使用。

1. 写一个复现旧会话仍有效的测试
   验证：测试先失败，且失败原因与现象一致
2. 实现会话失效逻辑
   验证：目标测试通过
3. 覆盖多会话、并发修改和重复修改
   验证：新增测试通过
4. 运行现有认证测试
   验证：无回归
```

可验证目标让执行者能够独立判断是否完成，也便于审查者复核证据。

## 使用边界

- 这些示例用于识别高频错误，不替代 OpenSpec specs、tasks、项目规则或人工验收。
- “最小实现”不意味着删除安全、权限、异步、迁移等风险要求的防御路径。
- 发现更简方案时先说明；是否采用仍由当前 change 的范围和用户确认决定。
